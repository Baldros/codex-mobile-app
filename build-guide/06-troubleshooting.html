Troubleshooting

When something fails, it's usually operation — not code. Start with the symptom in the table, confirm the probable cause and apply the fix. Then run the 5G checklist.

SSH connection & tunnel

SymptomProbable causeAction
SSH timeoutEndpoint closed, CGNAT or wrong addressValidate public/IPv6 address, NAT, router, or VPN.
SSH authenticates but health failsBridge stopped or wrong remote portTest the /health on the desktop and check the bridge loopback port.
PermitOpen denies the connectionRemote port other than the one releasedCheck that the forward points to the bridge loopback declared in the sshd_config.
Works on Wi-Fi, not 5GNAT/router/firewallTest the external endpoint of another network; consider VPN/overlay.

Failure of gradlew clean in CMake/autolinking

Typical symptom:

error
add_subdirectory given source ... /codegen/jni/ which is not an existing directory

That no it's SSH error — it's old incremental native state. Do the native reset and repeat the clean:

PowerShell Terminal 2common
cd <PROJECT_ROOT>\mobile\android

$targets = @("app\.cxx", "app\build\generated\autolinking")
foreach ($t in $targets) {
  if (Test-Path -LiteralPath $t) { Remove-Item -LiteralPath $t -Recurse -Force }
}

.\gradlew.bat clean --no-daemon --console=plain --stacktrace

A Wi-Fi IP appears as “Bridge”

In dev build this is normal (Metro), but no must occur in the APK release. Correct in this order:

  1. Confirm that EXPO_PUBLIC_BRIDGE_URL is not defined in the build terminal.
  2. Confirm that CODEX_MOBILE_API_BASE_URL and CODEX_MOBILE_SSH_TUNNEL_LOCAL_URL point to cell phone loopback.
  3. Clear data before installing: adb shell pm clear <APP_PACKAGE_ID>.
  4. Rebuild with the release flow.

Remember: in 5G the app continues talking to the local loopback. If the tunnel does not rise, the problem is in the route to SSH — not in the bridge URL.

When to ask for help

When reporting a problem, please include (no secrets): gateway mode, tunnel status (connecting/ready/error), if the /health responds on desktop, and the relevant excerpt from the sshd.log. This resolves most cases without exposing any credentials.
