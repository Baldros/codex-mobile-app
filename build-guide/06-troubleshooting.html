Chapter 6

Troubleshooting

When something fails, it's usually operation — not code. Start with the symptom in the table, confirm the probable cause and apply the fix. Then run the mobile-data checklist.

Tunnel & connectivity

SymptomProbable causeAction
Cannot parse IP address when saving the peerAn endpoint with a port was typed into Allowed IPsThat field takes CIDR only — no port, no brackets. The endpoint goes in Endpoint.
Handshake never completesPublic keys swapped between the two sidesThe device's peer holds the host's public key, and the host's peer block holds the device's.

Handshake completes, ping works, app stays offlineThe bridge is down, or bound to loopback instead of the tunnel addressCheck the listening address and /health. The network path is fine — this is a bridge problem.
Tunnel drops after a few idle minutesPersistent keepalive empty on the device's peerSet it to 25.
Tunnel stops working after a rebootTunnel service left on ManualSet the service to Automatic — chapter 3, section 5.
Handshake works on Wi-Fi, not on mobile dataEndpoint, IPv6 address or router firewallSee the checklist below — it goes through the causes in order.
Worked remotely, then stopped after some hoursDynamic DNS is publishing the temporary IPv6 addressThe updater must send the stable address explicitly — chapter 3, section 8.
Health fluctuatesComputer sleeping, or unstable networkDisable automatic sleep; the client already reconnects with backoff.
New device works and the old one stopsSame key or same /32 on two devicesOne key pair and one /32 per device.

Useful checks on the host — the first two need no elevation:

PowerShellcommon
Get-Service -Name 'WireGuardTunnel$<TUNNEL_NAME>' | Select-Object Name,Status,StartType
Get-NetUDPEndpoint -LocalPort <WG_PORT> | Select-Object LocalAddress,LocalPort
Get-NetTCPConnection -State Listen -LocalPort <BRIDGE_PORT> | Select-Object LocalAddress
PowerShelladmin
& "C:\Program Files\WireGuard\wg.exe" show <TUNNEL_NAME>

The repository also ships a script that runs all of this at once:

PowerShellcommon
.\scripts\validate_wireguard_ready.ps1
Do not diagnose with an online port checker

An open UDP port with a silent listener is indistinguishable from a filtered one, and a silent listener is exactly what WireGuard is. Port-check sites report "closed" or "filtered" with everything working perfectly. The only conclusive test is a real handshake: latest handshake in wg show.

Failure of gradlew clean in CMake/autolinking

Typical symptom:

error
add_subdirectory given source ... /codegen/jni/ which is not an existing directory

That is not a network error — it is stale incremental native state. Do the native reset and repeat the clean:

PowerShell Terminal 2common
cd <PROJECT_ROOT>\mobile\android

$targets = @("app\.cxx", "app\build\generated\autolinking")
foreach ($t in $targets) {
  if (Test-Path -LiteralPath $t) { Remove-Item -LiteralPath $t -Recurse -Force }
}

.\gradlew.bat clean --no-daemon --console=plain --stacktrace

The wrong address appears as “Bridge”

Almost always a saved preference, not a build problem: adb install -r keeps the app's stored settings, and the saved URL wins over the build-time default. Fix it in this order:

  1. In the app, Settings → Bridge, set the tunnel address and Save URL. This alone fixes most cases.
  2. Confirm EXPO_PUBLIC_BRIDGE_URL is not defined in the build terminal.
  3. Confirm CODEX_MOBILE_GATEWAY=http and that CODEX_MOBILE_API_BASE_URL points at the tunnel address.
  4. Only if it persists, rebuild with the release flow.

Clearing app data (pm clear) works too, but it wipes every other preference — treat it as a last resort, not a first step.

Remember: on mobile data the bridge address does not change. If the tunnel does not come up, the problem is the route to the WireGuard endpoint — not the Bridge URL in the app.

One thing this checklist cannot fix: if your mobile carrier does not provide IPv6 and your home IPv4 is behind CGNAT, there is no path in. That is a carrier limitation, not a configuration mistake — and it is not worth weakening a firewall to work around.

When to ask for help

When reporting a problem, include (with no secrets): the gateway mode, whether latest handshake appears in wg show, whether /health answers on the desktop, and which address the bridge is actually bound to. Those four facts separate a network problem from a bridge problem and resolve most cases without exposing anything.

Never paste a private key, a configuration file containing one, your public IPv6 address or your dynamic DNS name into a bug report.
