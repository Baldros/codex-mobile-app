Chapter 3

SSH Tunnel

SSH is the unique gateway that crosses the network. That's why he receives a user dedicated, one key per device and one sshd locked to only forward to the bridge. Do this chapter calmly — it's what protects your machine.

Why a dedicated user

Never use your primary Windows account for tunneling. A separate user gives:

  • Smaller impact radius — without administrative privileges, the credential is worth little if it is leaked.
  • Simple revocation — just remove a line from the authorized_keys of that device.
  • Focused hardening — you restrict this user in sshd without affecting the rest of the system.

1 · Create the dedicated user Administrator

Create a unique local tunnel account (here called <SSH_USER>, e.g.: codex_ssh). No add it to the Administrators group.

PowerShellAdministrator
# Ask for the password interactively, without leaving it in the history
$Password = Read-Host "Strong password for SSH user" -AsSecureString
New-LocalUser -Name "<SSH_USER>" -Password $Password `
  -Description "Dedicated user for the Codex Mobile SSH tunnel"

For the key profile to be ready, do a local login with that user once (or let the user step authorized_keys create the folder). So the folder C:\Users\<SSH_USER> comes into existence.

2 · Generate the SSH key Common terminal

Generate the key in your development user. Each device must have its own key, so it can be revoked separately.

Key format matters on Android

For the SSH client built into the APK, use a key RSA 4096 in PEM format. ED25519 switches work on ssh.exe on Windows, but may fail on the Android client with disconnection on pre-authentication. For interactive desktop testing, ED25519 is great.

PowerShellcommon
ssh-keygen -t rsa -b 4096 -m PEM `
  -f "$env:USERPROFILE\.ssh\codex_mobile_rsa" `
  -C "codex-mobile-<device>"
PowerShellcommon
ssh-keygen -t ed25519 `
  -f "$env:USERPROFILE\.ssh\codex_mobile_ed25519" `
  -C "codex-mobile-<device>"
About the passphrase

Leaving the passphrase blank is only justified because the key will be embedded in an automated build. In return, treat the .ssh\ as a secret: never version it, never copy it outside and revoke the key if the device leaves your control.

3 · Install the public key on the SSH user Administrator

Windows OpenSSH is strict with permissions: if the authorized_keys being “too open”, key login fails silently and drops to password. Do it exactly in this order.

Step A — write the key

PowerShellAdministrator
$sshUser = "<SSH_USER>"
$sshDir = "C:\Users\$sshUser\.ssh"
$authKeys = "$sshDir\authorized_keys"

# Secure the dedicated user's .ssh folder
New-Item -ItemType Directory -Path $sshDir -Force | Out-Null

# Read your PUBLIC key (.pub) and add it to authorized_keys
$pub = Get-Content "C:\Users\<YOUR_USER>\.ssh\codex_mobile_rsa.pub" -Raw
Add-Content -Path $authKeys -Value $pub -Encoding ascii

Step B — Fix Permissions (Critical)

Only the owner (<SSH_USER>) and the SISTEMA can access the file:

PowerShellAdministrator
$authKeys = "C:\Users\<SSH_USER>\.ssh\authorized_keys"

# 1. Take ownership to be able to change permissions
takeown /f $authKeys /a

# 2. Grants access to the owner user and the SYSTEM
icacls $authKeys /grant "<SSH_USER>:F"
icacls $authKeys /grant "SYSTEM:F"

# 3. Sets the owner user as the real owner
icacls $authKeys /setowner "<SSH_USER>"

# 4. Remove inheritance (clean up access from other users)
icacls $authKeys /inheritance:r

#5. Remove access from the Administrators group (SSH requires this)
icacls $authKeys /remove "Administrators"
Windows in English?

Swap Administrators put Administrators and SISTEMA put SYSTEM. List the correct names of your system with net localgroup.

4 · Validate local login Common terminal

Test the key through loopback. Must enter without asking for password:

PowerShellcommon
ssh -i "$env:USERPROFILE\.ssh\codex_mobile_rsa" <SSH_USER>@127.0.0.1

If it still asks for a password, the problem is usually with the permissions of the authorized_keys. View the server log and look for “bad ownership or modes”:

log path
C:\ProgramData\ssh\logs\sshd.log

5 · Hardening sshd Administrator

Edit C:\ProgramData\ssh\sshd_config and add a block that locks the tunnel user. The most important point is the PermitOpen: it guarantees that this credential can only forward to the bridge, and nothing else.

sshd_config
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
AllowUsers <SSH_USER>
Local AllowTcpForwarding
PermitOpen 127.0.0.1:<BRIDGE_PORT>
X11Forwarding no
AllowAgentForwarding no
MaxAuthTries 2
LoginGraceTime 20

Apply by restarting the service:

PowerShellAdministrator
Restart-Service sshd
DirectiveWhat it does
PasswordAuthentication noEliminates brute force online; only key enters.
AllowUsers <SSH_USER>Only the dedicated user can log in via SSH.
Local AllowTcpForwardingOnly allows local forward (what the tunnel uses).
PermitOpen 127.0.0.1:<BRIDGE_PORT>Restrict forward to bridge loopback — nothing else is reachable.
MaxAuthTries 2 / LoginGraceTime 20Reduces the window of attempts and idle connections.

If, due to the need for an internal build, you choose to PasswordAuthentication yes, this is only acceptable with a dedicated user, strong and unique password per dev, controlled firewall and PermitOpen maintained. Prefer key whenever possible.

6 · Remote access for 5G

To use the app outside the home, your cell phone needs a route to the sshd — and only up to SSH. The bridge continues in loopback. There are three paths, from safest to most laborious:

VPN/overlay recommended

A private network (e.g.: WireGuard/Tailscale) places your cell phone and desktop on the same logical network. You dial SSH over an overlay IP and don't open anything on the router.

direct IPv6

If both have public IPv6, the cell phone reaches the desktop via its IPv6 address, without port NAT. Maintain the firewall by only allowing SSH.

Port forwarding

The router forwards a public port you choose to the SSH port on the desktop. It works, but it exposes SSH to the internet — requires a strong password/key and monitoring.

In the app, you register the endpoints as a cascaded list (LAN, IPv6, VPN) and the client tries each one until it connects — details in the build chapter.

Regardless of the path, nothing HTTP is published. Even on 5G, the app talks to the local loopback and the bridge remains inaccessible directly via the internet.

7 · Revoke a device

If a device or build gets out of your control, remove the corresponding line from the authorized_keys — that's why each device has its own key. The revocation takes place on the server and takes immediate effect on subsequent connections.

PowerShellAdministrator
# Open the file and delete the key line for that device
notepad "C:\Users\<SSH_USER>\.ssh\authorized_keys"
