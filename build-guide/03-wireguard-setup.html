Chapter 3

WireGuard VPN

WireGuard is the only thing that crosses the network. The phone joins a private network that exists solely between key-authenticated peers, and talks to the bridge inside it. No credential is embedded in the app, and the bridge is never published.

Why a VPN instead of an SSH tunnel

Two facts decide this, and neither is a matter of taste.

First: most residential connections are behind CGNAT (RFC 6598, the 100.64.0.0/10 range). Under CGNAT there is no IPv4 port forwarding — not for SSH, not for anything. The zero-cost path in is IPv6, which is native and un-NATted on most modern links.

Second: over IPv6 the service sits on the open internet with no NAT in front of it. At that point, what you expose stops being a detail.

Exposed sshdExposed WireGuard
Reply to a scannerVersion banner and OSComplete silence
Pre-auth surfaceFull SSH parserNoise_IK handshake, small codebase
Credential in the APKYes — extractable from the binaryNone — the key is born on the device
Invalid packetError / negotiationDropped with no response
Revoke a deviceEdit authorized_keysDelete a [Peer] block
Rotate a credentialRebuild and redistribute the APKChange one line on the host
The decisive difference is the credential

WireGuard being quiet is nice. What actually changes the security model is that the phone's private key is generated inside the WireGuard app and never leaves the device — so there is nothing left in the APK to extract.

The topology you are building

One private network, two peers, one open port.

Android phone
10.77.77.2/32 inside the tunnel
WireGuard · UDP 51821 · split route to 10.77.77.1/32 only
Desktop · trust boundary
wg-codex
10.77.77.1/24 · the only service reachable from outside
Codex Bridge
bound to 10.77.77.1 — never 0.0.0.0
@openai/codex-sdk · app-server · exec
internal runtime (interchangeable)
  • The bridge listens only on the tunnel address. Not on the LAN, not on the internet.
  • The phone routes only 10.77.77.1/32 through the tunnel — a split tunnel, not 0.0.0.0/0. The rest of the phone's traffic is untouched.
  • There is no NAT, no PostUp/PostDown, no DNS, no forwarding. That is deliberate: less configuration is less to audit.
Never forward the bridge port

The only port that may ever reach your router from the internet is UDP 51821. Forwarding TCP 8787 would publish an API that currently has no authentication at all — see the security chapter.

1 · Install WireGuard Administrator

On the desktop:

PowerShelladmin
winget install --id WireGuard.WireGuard -e

Confirm it:

PowerShellcommon
& "C:\Program Files\WireGuard\wg.exe" --version

On the phone, install the official app from the store:

Android
Name:      WireGuard
Publisher: WireGuard Development Team
Package:   com.wireguard.android

The app is free and open source. No paid VPN subscription is involved — your desktop is the server. Note that Android allows only one active VPN service per profile.

2 · Generate the host key Common terminal

The private key must never appear on screen, never enter shell history, and never enter the repository. Redirect it straight into a file, outside the repo:

PowerShellcommon
$KeyDir  = "$env:USERPROFILE\.wireguard"
$KeyFile = Join-Path $KeyDir "wg-codex.key"
New-Item -ItemType Directory -Force -Path $KeyDir | Out-Null

& cmd /c "`"C:\Program Files\WireGuard\wg.exe`" genkey > `"$KeyFile`""

Restrict the ACL to your user only:

PowerShellcommon
icacls $KeyFile /inheritance:r
icacls $KeyFile /grant:r "$env:USERNAME:(F)"
icacls $KeyFile

Derive the public key — which is safe to display:

PowerShellcommon
$Pub = (& cmd /c "`"C:\Program Files\WireGuard\wg.exe`" pubkey < `"$KeyFile`"" 2>&1) |
  Select-Object -First 1
$Pub
Do not pipe into wg pubkey

In PowerShell 5.1, Get-Content $KeyFile | wg pubkey appends a newline to the executable's stdin and fails with Trailing characters found after key. Use the cmd redirection above.

3 · Create the tunnel on the phone

In the WireGuard app: + → Create from scratch.

FieldValue
Namecodex-mobile
Private keyGenerate it in the app
Addresses10.77.77.2/32
DNSempty
Listen portempty

Copy only the public key. Then add a peer:

Peer fieldValue
Public keythe host's public key from step 2
Preshared keyempty (optional hardening — see chapter 5)
Endpointyour desktop's LAN IP and port 51821, for the first test
Allowed IPs10.77.77.1/32
Persistent keepalive25
The three mistakes everyone makes in this form

Endpoint in the Allowed IPs field. That field takes CIDR only — no port, no brackets. Pasting [2804:...]:51821 there returns Cannot parse IP address.

The host's public address in Allowed IPs. That routes the endpoint itself into the tunnel and creates a loop; the handshake stops completing.

0.0.0.0/0 in Allowed IPs. That sends all of the phone's traffic through your desktop. Not this design.

/32 is a CIDR prefix meaning one address. It is not a port. And Persistent keepalive 25 means one authenticated maintenance packet every 25 seconds while idle — not a 25-second connection. It keeps router and carrier NAT mappings alive, which is what matters on mobile data.

4 · Write the host configuration Common terminal

Outside the repository, with a restricted ACL:

PowerShellcommon
$ConfPath = "$env:USERPROFILE\wg-codex.conf"
$PhoneKey = "<paste the phone's public key>"
$Priv     = (Get-Content $KeyFile -Raw).Trim()

@"
[Interface]
Address = 10.77.77.1/24
ListenPort = 51821
PrivateKey = $Priv

[Peer]
PublicKey = $PhoneKey
AllowedIPs = 10.77.77.2/32
"@ | Set-Content -Path $ConfPath -Encoding ascii

Remove-Variable Priv
icacls $ConfPath /inheritance:r
icacls $ConfPath /grant:r "$env:USERNAME:(F)"

On the host side, AllowedIPs is a source filter, not a route: it declares which addresses that peer is allowed to speak from. One /32 per device is what stops one peer from impersonating another.

Import it: open the WireGuard GUI → Import tunnel(s) from file.

The Windows import dialog handles long paths badly. If it cannot find the file, copy it somewhere short first. After importing, delete your copy — the service keeps its own, and the file you wrote contains the private key in plain text.

5 · Make it survive reboots Administrator

Activating the tunnel creates a Windows service named after it:

Get-Service -Name 'WireGuardTunnel$wg-codex' | Select-Object Name,Status,StartType

Output

6 · Firewall: nothing to do Common terminal

This is where Windows differs from the Linux write-ups you may have read. On Linux you add UFW rules. On Windows you create no firewall rule at all.

WireGuard for Windows installs its own filters in the Windows Filtering Platform when the tunnel comes up, and removes them when it goes down. Those filters do not appear in Defender Firewall. Searching for a "WireGuard" rule and finding nothing is the correct outcome:

PowerShellcommon
Get-NetFirewallRule -DisplayName "*ireGuard*"   # returns nothing

What you verify instead is the actual listener:

PowerShellcommon
Get-NetUDPEndpoint -LocalPort 51821 | Select-Object LocalAddress,LocalPort
Output
LocalAddress LocalPort
------------ ---------
::                51821
0.0.0.0           51821

The :: line is what makes the IPv6 endpoint work on mobile data.

7 · Validate on Wi-Fi Common terminal

Activate the tunnel on the phone, then from the desktop:

PowerShellcommon
Test-Connection 10.77.77.2 -Count 3

To inspect the handshake itself, you need an elevated terminal:

PowerShelladmin
& "C:\Program Files\WireGuard\wg.exe" show wg-codex
Output
interface: wg-codex
  public key: <host public key>
  listening port: 51821

peer: <phone public key>
  endpoint: 192.168.1.5:43521
  allowed ips: 10.77.77.2/32
  latest handshake: 12 seconds ago
  transfer: 1.20 KiB received, 976 B sent

Without elevation, wg show returns Permission denied. That is expected and says nothing about the tunnel. Also note the phone's source port is ephemeral — it does not need to equal 51821.

A missing latest handshake means no valid packet arrived. That is a network-path problem, never a bridge problem.

8 · Access over mobile data

Only the phone's Endpoint changes. Allowed IPs stays 10.77.77.1/32.

Pick the right IPv6 address

PowerShellcommon
Get-NetIPAddress -AddressFamily IPv6 |
  Where-Object { $_.PrefixOrigin -eq 'RouterAdvertisement' } |
  Select-Object IPAddress,SuffixOrigin,ValidLifetime

You will see two global addresses, and the difference matters:

SuffixOriginWhat it isUse as endpoint?
LinkStable, derived from the hardware (EUI-64)Yes
RandomTemporary privacy address (RFC 8981)No — it rotates

In the phone's peer, set the Endpoint to [<stable IPv6>]:51821. Brackets are mandatory for IPv6 with a port.

Router pinhole

IPv6 has no NAT, so there is no "port forward" — what exists is the router's inbound firewall, and what you need is an exception: allow inbound UDP 51821 to the stable address. Many ISP routers ship with a permissive IPv6 firewall and need nothing at all. Check before changing anything, and never open TCP 8787.

Online port checkers cannot test this

An open UDP port with a silent listener is indistinguishable from a filtered one — and a silent listener is exactly what WireGuard is. Port-check sites will report "closed" or "filtered" with everything working correctly.

The only conclusive test is a real handshake: turn Wi-Fi off on the phone, activate the tunnel, and check latest handshake on the host.

Dynamic DNS, and the trap in it

ISPs renumber IPv6 prefixes. To avoid reconfiguring the phone every time, publish an AAAA record via a free dynamic DNS provider and use <your-host>:51821 as the endpoint — no brackets, since it is now a name.

The trap: any updater running in "detect my IP automatically" mode publishes the temporary address, not the stable one. The tunnel then works for a few hours and stops. The updater must send the stable address explicitly:

PowerShellcommon
$Stable = (Get-NetIPAddress -AddressFamily IPv6 |
  Where-Object { $_.PrefixOrigin -eq 'RouterAdvertisement' -and $_.SuffixOrigin -eq 'Link' } |
  Select-Object -First 1).IPAddress

# then send $Stable to your DDNS provider's update endpoint,
# keeping the token out of the repository

9 · Add, rotate and revoke devices

All three are edits to the host configuration followed by a service restart. No rebuild, no reinstall.

OperationWhat you do
Add a deviceAppend a [Peer] block with its public key and its own /32
Rotate a keyRegenerate the key on the device; replace PublicKey in that block
Revoke a deviceDelete that [Peer] block
PowerShelladmin
Stop-Service 'WireGuardTunnel$wg-codex'
Start-Service 'WireGuardTunnel$wg-codex'
& "C:\Program Files\WireGuard\wg.exe" show wg-codex

Revocation is immediate and does not depend on the device cooperating: even with the tunnel still configured on its side, the host silently drops its packets.

Comment every peer block

Write the device name and the date above each [Peer]. Six months from now an anonymous base64 key is impossible to attribute, and nobody feels safe deleting it — so it stays forever. Give every device its own /32, and never reuse a revoked one without removing the old block first.
