Chapter 1

Architecture & decisions

Before installing anything, it is worth understanding why the app is designed like this. Reliable transportation and border choices are what make it safe to operate Cell phone codex — including 5G.

Objective

Create an internal mobile app that controls a local Codex CLI session running on the developer machine. The app is a operation customer: it sends prompts, approves actions and tracks execution, but does not host any intelligence or sensitive credentials.

The desktop is the frontier of trust

Everything sensitive remains on the desktop. The phone never receives credentials from OpenAI.

Stays on the desktop

Codex CLI, OpenAI login and credentials, local workspace, shell/filesystem permissions and the bridge that translates commands.

Stay on mobile

Operation UI, the local end of the SSH tunnel, non-sensitive preferences, and — in internal profile — the built-in SSH credential.

Out of scope

  • Expose the OpenAI API directly on mobile.
  • Run the Codex SDK within the mobile app.
  • Open the bridge on the public network.
  • Build a multi-tenant or commercial product at this stage.

Why an SSH Tunnel

The tunnel pattern solves both the remote access and the attack surface at once:

  • No HTTP on the internet. Bridge is never published; it only listens to the desktop loopback.
  • It works on 5G. As long as there is a valid SSH route to the machine, the app dials the SSH endpoint and the local forward delivers the HTTP as if it were local.
  • Loopback on both ends. On your cell phone, the app talks to 127.0.0.1; on the desktop the bridge responds in 127.0.0.1. The tunnel is the only thing in between.
  • Minimum surface. With PermitOpen restricted, the app's credential can only forward to the bridge port — and nothing else.

In 5G, the bridge does not change address. The app continues talking to the local loopback — only the SSH endpoint used underneath the tunnel changes.

The client also inherits mature operational standards: IPv4/IPv6 endpoint fallback, periodic health check, reconnection with backoff and short diagnostic logs.

SSE as a streaming contract

The bridge delivers events via Server-Sent Events. This keeps the customer simple and covers incremental messages, tool status, approval requests, errors, heartbeats and completion.

The run belongs to the backend, not the connection

The Codex run runs on the desktop. The SSE is just one temporary subscription about this run. If the cell phone changes screen, closes or loses network, the run continues — only for termination, failure, pending approval or explicit cancellation.

Native Codex History

The bridge does not create persistence of its own of conversations. The permanent history comes from Codex itself (in ~/.codex/sessions), exposed via codex app-server. The bridge only normalizes routes such as listing, reading and resuming threads, and only keeps the ephemeral state in memory of active runs, SSE and pending approvals.

Components

Mobile App
  • Keep a local port forward SSH.
  • View shipping status.
  • Consume HTTP/SSE from the bridge; send prompts, cancellations and approvals.
  • Persist non-sensitive local preferences.
  • Store/embed the SSH credential according to the chosen internal profile.
Codex Bridge
  • Run locally and link only to loopback.
  • Normalize a stable HTTP/SSE API for mobile.
  • Encapsulate differences between Codex SDK, app-server and exec.
  • Control cancellation, heartbeats and thread history.

Stack: Node.js 18+, TypeScript and @openai/codex-sdk as the preferred path to MVP.

Codex Runtime
  • @openai/codex-sdk — preferred for programmatic MVP.
  • codex app-server — rich experience with events, history, and approvals (JSON-RPC 2.0; parts marked as experimental).
  • codex exec --json — stable fallback for non-interactive tasks.

The mobile contract remains HTTP/SSE even if the internal runtime changes — the app does not depend on the app-server protocol.

Trust Model

Mobile is only trusted as an internal client. It does not receive OpenAI credentials. The loss of phone or APK can compromise the built-in SSH credential, but no must open access broad if sshd is restricted to a dedicated user and a PermitOpen pointing only for bridge loopback. Details of this hardening are in the SSH tunnel chapter and in security page.
