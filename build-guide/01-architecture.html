Capítulo 1

Arquitetura & decisões

Antes de instalar qualquer coisa, vale entender por que o app é desenhado assim. As escolhas de transporte e de fronteira de confiança são o que torna seguro operar o Codex do celular — inclusive em 5G.

Objetivo

Criar um app mobile interno que controle uma sessão local do Codex CLI rodando na máquina do desenvolvedor. O app é um cliente de operação: ele envia prompts, aprova ações e acompanha a execução, mas não hospeda nenhuma inteligência nem credencial sensível.

O desktop é a fronteira de confiança

Tudo que é sensível permanece no desktop. O celular nunca recebe credenciais da OpenAI.

Fica no desktop

Codex CLI, login e credenciais OpenAI, workspace local, permissões de shell/filesystem e o bridge que traduz comandos.

Fica no mobile

UI de operação, a ponta local do túnel SSH, preferências não sensíveis e — em perfil interno — a credencial SSH embutida.

Fora de escopo

  • Expor a API da OpenAI diretamente no mobile.
  • Rodar o Codex SDK dentro do app mobile.
  • Abrir o bridge na rede pública.
  • Construir um produto multi-tenant ou comercial nesta fase.

Desenho alvo

O tráfego HTTP entre o app e o bridge trafega por 127.0.0.1 nas duas pontas do túnel. O único serviço alcançável remotamente é o SSH; o HTTP nunca toca a internet.

Por que um túnel SSH

O padrão de túnel resolve, de uma vez, o acesso remoto e a superfície de ataque:

  • Nada de HTTP na internet. O bridge nunca é publicado; ele só escuta no loopback do desktop.
  • Funciona em 5G. Desde que exista uma rota SSH válida até a máquina, o app discа o endpoint SSH e o forward local entrega o HTTP como se fosse local.
  • Loopback nas duas pontas. No celular o app fala com 127.0.0.1; no desktop o bridge responde em 127.0.0.1. O túnel é a única coisa no meio.
  • Superfície mínima. Com PermitOpen restrito, a credencial do app só consegue encaminhar para a porta do bridge — e nada mais.

No 5G, o bridge não muda de endereço. O app continua falando com o loopback local — quem muda é apenas o endpoint SSH usado por baixo do túnel.

Gateway de transporte

O mobile abstrai o transporte em três modos, e toda chamada ao bridge passa antes por ensureTransportReady:

ModoPara que serve
mockDesenvolvimento de UI sem backend real.
httpAcesso local direto durante o desenvolvimento.
ssh_tunnelModo real de produção interna — o que este guia configura.

O cliente também herda padrões operacionais maduros: fallback de endpoints IPv4/IPv6, health check periódico, reconexão com backoff e logs curtos de diagnóstico.

SSE como contrato de streaming

O bridge entrega eventos por Server-Sent Events. Isso mantém o cliente simples e cobre mensagens incrementais, status de ferramenta, pedidos de aprovação, erros, heartbeats e conclusão.

A run pertence ao backend, não à conexão

A run do Codex roda no desktop. O SSE é só uma assinatura temporária sobre essa run. Se o celular troca de tela, fecha ou perde rede, a run continua — só para por término, falha, aprovação pendente ou cancelamento explícito.

Histórico nativo do Codex

O bridge não cria persistência própria de conversas. O histórico permanente vem do próprio Codex (em ~/.codex/sessions), exposto via codex app-server. O bridge apenas normaliza rotas como listar, ler e retomar threads, e mantém em memória só o estado efêmero de runs ativas, SSE e aprovações pendentes.

Componentes

Mobile App
  • Manter um local port forward SSH.
  • Exibir o status do transporte.
  • Consumir HTTP/SSE do bridge; enviar prompts, cancelamentos e aprovações.
  • Persistir preferências locais não sensíveis.
  • Armazenar/embutir a credencial SSH conforme o perfil interno escolhido.
Codex Bridge
  • Rodar localmente e vincular somente ao loopback.
  • Normalizar uma API HTTP/SSE estável para o mobile.
  • Encapsular diferenças entre Codex SDK, app-server e exec.
  • Controlar cancelamento, heartbeats e histórico de threads.

Stack: Node.js 18+, TypeScript e @openai/codex-sdk como caminho preferencial do MVP.

Codex Runtime
  • @openai/codex-sdk — preferido para o MVP programático.
  • codex app-server — experiência rica com eventos, histórico e aprovações (JSON-RPC 2.0; partes marcadas como experimentais).
  • codex exec --json — fallback estável para tarefas não interativas.

O contrato mobile permanece HTTP/SSE mesmo que o runtime interno mude — o app não depende do protocolo do app-server.

Modelo de confiança

O mobile é confiável apenas como cliente interno. Ele não recebe credenciais OpenAI. A perda do celular ou do APK pode comprometer a credencial SSH embutida, mas não deve abrir acesso amplo se o sshd estiver restrito a um usuário dedicado e a um PermitOpen apontando só para o loopback do bridge. Os detalhes desse hardening estão no capítulo do túnel SSH e na página de segurança.
