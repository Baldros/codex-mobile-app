Chapter 1

Architecture & decisions

Before installing anything, it is worth understanding why the app is designed like this. Reliable transportation and border choices are what make it safe to operate Cell phone codex — including 5G.

Objective

Create an internal mobile app that controls a local Codex CLI session running on the developer machine. The app is a operation customer: it sends prompts, approves actions and tracks execution, but does not host any intelligence or sensitive credentials.

The desktop is the frontier of trust

Everything sensitive remains on the desktop. The phone never receives credentials from OpenAI.

Stays on the desktop

Codex CLI, OpenAI login and credentials, local workspace, shell/filesystem permissions and the bridge that translates commands.

Stay on mobile

Operation UI, non-sensitive preferences, and the WireGuard private key — generated on the device by the WireGuard app, never by this project.

Out of scope

  • Expose the OpenAI API directly on mobile.
  • Run the Codex SDK within the mobile app.
  • Open the bridge on the public network.
  • Build a multi-tenant or commercial product at this stage.

Target drawing

HTTP traffic between the app and the bridge travels inside a private network that exists only between key-authenticated peers. The only remotely reachable service is WireGuard; HTTP never touches the internet.

Why a VPN

The tunnel pattern solves remote access and attack surface at once:

  • No HTTP on the internet. The bridge is never published; it binds only to its address inside the private network.
  • It works on mobile data. As long as there is a reachable endpoint for the desktop, the phone completes a handshake and the private address becomes routable — from anywhere.
  • Nothing to extract from the APK. The device's private key is generated by the WireGuard app and never leaves the phone. The build carries no credential at all.
  • Silent to scanners. WireGuard does not answer packets that carry no valid key. From outside, the port is indistinguishable from a closed one.
  • Minimum surface. One UDP port, a split route that carries only the host address, and no NAT or forwarding rules to get wrong.

On mobile data, the bridge does not change address. The app keeps talking to the same private address — only the WireGuard endpoint underneath changes.

This replaced an SSH tunnel

Earlier versions of this guide used an SSH local port forward with a credential embedded in the APK. It was replaced because CGNAT makes IPv6 the only viable way in, and over IPv6 an extractable credential plus a service that announces its version is the wrong pair of properties to expose. Chapter 3 has the full comparison.

Transport gateway

The mobile abstracts transport into three modes, and every call to the bridge first passes through ensureTransportReady:

ModeWhat is it for
mockUI development without real backend.
httpDirect HTTP — over the tunnel in real use, over loopback in development. What this guide sets up.
ssh_tunnelLegacy. Still in the codebase, outside the supported path.

The client also keeps mature operational standards: periodic health check, reconnection with backoff and short diagnostic logs. With http, ensureTransportReady resolves immediately — there is no transport for the app to bring up, because the OS already did it.

SSE as a streaming contract

The bridge delivers events via Server-Sent Events. This keeps the customer simple and covers incremental messages, tool status, approval requests, errors, heartbeats and completion.

The run belongs to the backend, not the connection

The Codex run runs on the desktop. The SSE is just one temporary subscription about this run. If the cell phone changes screen, closes or loses network, the run continues — only for termination, failure, pending approval or explicit cancellation.

Native Codex History

The bridge does not create persistence of its own of conversations. The permanent history comes from Codex itself (in ~/.codex/sessions), exposed via codex app-server. The bridge only normalizes routes such as listing, reading and resuming threads, and only keeps the ephemeral state in memory of active runs, SSE and pending approvals.

Components

Mobile App
  • Consume HTTP/SSE from the bridge over the tunnel address.
  • View transport status.
  • Send prompts, cancellations and approvals.
  • Persist non-sensitive local preferences.
  • Not manage the tunnel. That belongs to the WireGuard app, outside this project — which is why the build carries no secret.
Codex Bridge
  • Run locally and bind only to the tunnel address — never 0.0.0.0.
  • Normalize a stable HTTP/SSE API for mobile.
  • Encapsulate differences between Codex SDK, app-server and exec.
  • Control cancellation, heartbeats and thread history.

Stack: Node.js 18+, TypeScript and @openai/codex-sdk as the preferred path to MVP.

Codex Runtime
  • @openai/codex-sdk — preferred for programmatic MVP.
  • codex app-server — rich experience with events, history, and approvals (JSON-RPC 2.0; parts marked as experimental).
  • codex exec --json — stable fallback for non-interactive tasks.

The mobile contract remains HTTP/SSE even if the internal runtime changes — the app does not depend on the app-server protocol.

Trust Model

Mobile is only trusted as an internal client. It receives no OpenAI credentials and, in this design, carries no secret from this project at all. Losing the phone exposes its WireGuard private key — protected by the screen lock and the Android keystore — and revoking it is immediate and unilateral from the host.

Know the boundary you are relying on

The cryptographic boundary is currently the only boundary. The bridge has no HTTP authentication, so anything that reaches its address — including any process on the desktop itself — has full control. Read the security chapter before deciding this is acceptable for your situation.
