Capítulo 5

Segurança

Embutir uma credencial SSH no app não é problema técnico — é uma decisão de segurança. Esta página define quando isso é aceitável, quando vira risco grave e quais controles tornam o perfil interno defensável.

A premissa

Qualquer senha, chave privada ou token colocado dentro do APK, bundle, asset, constante de build ou storage local deve ser tratado como recuperável por quem tiver acesso ao binário, ao aparelho, a um backup ou a um ambiente de debug.

Para este projeto interno, a decisão é suportar credencial embutida como perfil de build interno — desde que o risco seja limitado por configuração do sshd, usuário dedicado e rotação.

Quando é aceitável

Aceitável para uso interno quando todas as condições abaixo são verdadeiras:

  • Cada dev gera a própria credencial.
  • Cada dev builda o próprio app (ou recebe build individual).
  • A credencial é por usuário ou por dispositivo.
  • O usuário SSH é dedicado ao túnel — nunca a conta principal do sistema.
  • O sshd restringe o forward com PermitOpen apontando só para o loopback do bridge.
  • O bridge fica vinculado somente ao loopback.
  • O host key do servidor é pinado ou validado no primeiro pareamento.
  • Existe um processo simples de revogação.
  • O APK não é compartilhado fora da equipe.

Quando vira risco grave

  • A mesma senha/chave é compartilhada por vários usuários.
  • A credencial permite login em conta administrativa ou pessoal do dev.
  • O sshd permite forward amplo para qualquer host/porta.
  • O SSH fica exposto na internet com senha fraca e sem rate limit.
  • Não há rotação quando um aparelho ou build vaza.
  • O app é distribuído fora da equipe interna.
  • Segredos são commitados no repositório.

Senha × chave privada

  • Permite revogar por dispositivo via authorized_keys.
  • Com PasswordAuthentication no, elimina brute force.
  • Continua extraível do app se embutida — cuide do armazenamento.

Preferência técnica: chave por dispositivo (ou por dev) com PasswordAuthentication no.

  • Mais simples para builds manuais e fácil de rotacionar.
  • Mais sujeita a ataque online se o SSH estiver exposto sem rate limit.
  • Não permite revogar um dispositivo sem trocar a senha daquele usuário.

Opção aceita só na fase interna: senha por dev em build próprio, com hardening e rotação.

Controles obrigatórios

A config de build exige uma confirmação explícita e a declaração do modo de autenticação:

variáveis de build
CODEX_MOBILE_ALLOW_EMBEDDED_SSH_SECRET=true
CODEX_MOBILE_SSH_AUTH_MODE=private_key   # ou: password

O app deve mostrar na tela de diagnóstico que está em perfil interno com credencial embutida — sem nunca revelar o valor.

Use variáveis de ambiente, não arquivos versionados

Segredos entram no build pelo ambiente do terminal e são lidos de arquivos locais — nunca digitados em código ou docs. Boas práticas no PowerShell:

1

Leia a chave de arquivo, não a cole inline:

PowerShellcomum
$env:CODEX_MOBILE_SSH_PRIVATE_KEY_PEM = Get-Content "$env:USERPROFILE\.ssh\codex_mobile_rsa" -Raw
2

Escolha o escopo certo. Variáveis de sessão ($env:VAR) somem ao fechar o terminal — ótimo para segredos. Só promova a User/Machine o que não for sensível (como JAVA_HOME).

3

Limpe as variáveis sensíveis ao terminar o build:

PowerShellcomum
Remove-Item Env:\CODEX_MOBILE_SSH_PRIVATE_KEY_PEM -ErrorAction SilentlyContinue
Remove-Item Env:\CODEX_MOBILE_SSH_PASSWORD       -ErrorAction SilentlyContinue

Regras de repositório

  • Nunca commitar .env, .env.local, keystores, chaves privadas ou senhas.
  • Manter um .env.example sem valores reais.
  • Preferir injeção por CI, script local ou parâmetro de build da stack escolhida.
  • Tratar logs como sensíveis — eles podem capturar segredos sem querer.

Adicione .ssh/, *.pem, *.env e a pasta de keystores ao .gitignore antes do primeiro commit, e rode uma varredura de segredos antes de publicar qualquer mudança.

Rede & rotação

  • Só o SSH cruza a rede. O bridge permanece no loopback; prefira VPN/overlay a abrir portas no roteador.
  • Senhas fortes e únicas por dev, quando houver senha.
  • Rotacione a credencial quando um aparelho ou build sair do controle do usuário.
  • Pinagem de host key (ou trust-on-first-use no pareamento) evita servidores falsos.

Credencial embutida aumenta a manutenção: rotação costuma exigir rebuild, e builds antigos seguem válidos até a credencial ser revogada no servidor. Documente onde está a sua chave e mantenha o processo de revogação à mão.
