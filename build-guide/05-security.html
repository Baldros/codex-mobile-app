Chapter 5

Security

Embedding an SSH credential in the app is not a technical problem — it is a security decision. This page defines when this is acceptable, when it becomes a serious risk and what controls make it defensible internal profile.

The premise

Any password, private key or token placed within the APK, bundle, asset, build constant or local storage must be treated as recoverable by anyone who has access to the binary, the device, a backup or a debug environment.

For this internal project, the decision is to support built-in credential as internal build profile — as long as risk is limited by system configuration sshd, dedicated user and rotation.

When is it acceptable

Acceptable for internal use when all the conditions below are true:

  • Each dev generates their own credential.
  • Each dev builds their own app (or receives an individual build).
  • The credential is per user or per device.
  • The SSH user is dedicated to the tunnel — never the primary account on the system.
  • O sshd restricts the forward with PermitOpen pointing only to the bridge loopback.
  • The bridge is only linked to the loopback.
  • The server host key is pinned or validated on the first pairing.
  • There is a simple revocation process.
  • The APK is not shared outside the team.

When it becomes a serious risk

  • The same password/key is shared by multiple users.
  • The credential allows login to the dev's administrative or personal account.
  • O sshd allows wide forward to any host/port.
  • SSH is exposed to the internet with a weak password and no rate limit.
  • There is no rotation when a device or build leaks.
  • The app is distributed outside the internal team.
  • Secrets are committed to the repository.

Password × private key

  • Allows you to revoke by device via authorized_keys.
  • With PasswordAuthentication no, eliminates brute force.
  • It remains extractable from the app if embedded — take care of storage.

Technical preference: key per device (or per dev) with PasswordAuthentication no.

  • Simpler for manual builds and easier to rotate.
  • More subject to online attack if SSH is exposed without rate limit.
  • It does not allow revoking a device without changing that user's password.

Option only accepted in the internal phase: password per dev in own build, with hardening and rotation.

Mandatory controls

The build config requires explicit confirmation and authentication mode declaration:

build variables
CODEX_MOBILE_ALLOW_EMBEDDED_SSH_SECRET=true
CODEX_MOBILE_SSH_AUTH_MODE=private_key # or: password

The app should show on the diagnostic screen that it is in internal profile with embedded credential — without ever revealing the value.

Use environment variables, not versioned files

Secrets enter the build through the terminal environment and are read from local files — never typed into code or docs. Good practices in PowerShell:

1

Read the file key, don't paste it inline:

PowerShellcommon
$env:CODEX_MOBILE_SSH_PRIVATE_KEY_PEM = Get-Content "$env:USERPROFILE\.ssh\codex_mobile_rsa" -Raw
2

Choose the right scope. Session variables ($env:VAR) disappear when closing the terminal — great for secrets. Just promote User/machine what is not sensitive (such as JAVA_HOME).

3

Clean sensitive variables when finishing the build:

PowerShellcommon
Remove-Item Env:\CODEX_MOBILE_SSH_PRIVATE_KEY_PEM -ErrorAction SilentlyContinue
Remove-Item Env:\CODEX_MOBILE_SSH_PASSWORD -ErrorAction SilentlyContinue

Repository Rules

  • Never commit .env, .env.local, keystores, private keys or passwords.
  • Keep a .env.example no real values.
  • Prefer injection via CI, local script or build parameter of the chosen stack.
  • Treat logs as sensitive — they can capture secrets unintentionally.

Add .ssh/, *.pem, *.env and the keystores folder to .gitignore before the first commit, and run a secrets scan before publishing any changes.

Network & Rotation

  • Only SSH crosses the network. The bridge remains in loopback; prefer VPN/overlay to opening ports on the router.
  • Strong and unique passwords by dev, when there is a password.
  • Rotate the credential when a device or build leaves the user's control.
  • Host key pinout (or trust-on-first-use in peering) prevents fake servers.

Embedded credentials increase maintenance: rotation usually requires rebuilding, and old builds remain valid until the credential is revoked on the server. Document where your key is and keep the revocation process handy.
