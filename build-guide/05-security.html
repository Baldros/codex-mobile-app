Chapter 5

Security

This page is deliberately honest about what this design protects and what it does not. The WireGuard transport is strong. The application behind it currently has no authentication at all — read this before you decide the setup is good enough for your situation.

What is actually at stake

This is not a chat app. The bridge is a path to code execution with your desktop user's privileges. Sizing the risk starts with naming the assets:

AssetWhere it livesImpact if compromised
Codex / OpenAI credentialdesktop user profileaccount misuse, cost, access to history
Desktop filesystemyour drivesreading and writing code, secrets, keys
Command executionCodex app-serverarbitrary execution as the logged-in user
Conversation history~/.codex/sessionsleak of working context
Host WireGuard keyhost, restricted ACLimpersonating the host
Device WireGuard keyAndroid keystoreaccess to the private network

One boundary, and only one

Everything that reaches the bridge's address has full control of it. The authenticated WireGuard peer plus the bind address is the security model — there is no second layer behind it.

The bridge has no HTTP authentication

No token, no session, no pairing — and it replies with Access-Control-Allow-Origin: *. Two consequences follow, and both are easy to miss:

Any process on the desktop can reach it. Binding to the tunnel address restricts access over the network, but that address is local to the host: a downloaded binary, a browser extension, a compromised npm package in an unrelated project — all have the same access your phone does.

Any web page open on the phone can reach it while the tunnel is up, because the phone routes the host address through the tunnel for every app, browser included. With a wildcard CORS policy, JavaScript on an arbitrary site can call the API and read the responses.

This is precisely what NIST's Zero Trust Architecture (SP 800-207) argues against: network location should never imply authorization. The design here is a classic perimeter, with all the power concentrated at the entrance.

What the WireGuard design does fix

The migration away from an SSH tunnel was not cosmetic. It closed a real class of problem:

Before (SSH tunnel)Now (WireGuard)
Private key embedded in the APK, extractable from the binaryNo secret in the APK; the key is born on the device
Rotating a credential meant rebuilding and redistributingRotating is one line on the host
The exposed service announced its version to any scannerNo reply to packets without a valid key
Pre-auth surface: a full SSH implementationNoise_IK handshake, no cipher negotiation, small codebase
Revocation meant editing a user's authorized_keysRevocation is deleting a [Peer] block, effective immediately

Structurally, the model moved from "shared secret shipped inside the client" — the classic CWE-798, hard-coded credentials — to one key pair per device. Removing a class of problem beats mitigating it.

Known gaps

Stated plainly, so nobody has to discover them the hard way.

No authentication on the API High

No route checks a credential, and CORS is wide open. Anything that can reach the address can list and add workspaces, read configuration, start Codex runs and answer approvals.

Fix: a shared token compared in constant time, required on every /v1/* route; drop the wildcard CORS (a native client does not need CORS at all); validate the Host header against an allowlist.

References: CWE-306, CWE-942 · OWASP API Security Top 10 API2, API5 · OWASP ASVS V13.

Filesystem browsing is not scoped High

The directory-browsing endpoints are not restricted to the workspace allowlist, and the workspace list can be widened through the API itself. Combined with the gap above, an unauthenticated caller can map the machine and then expand its own scope.

Fix: scope browsing to permitted roots; make widening the allowlist require confirmation on the desktop rather than being a plain remote call.

References: CWE-285, CWE-538 · OWASP API Security API1 · least privilege (Saltzer & Schroeder).

No guard against a public bind Medium

The default bind address is safe, but nothing rejects 0.0.0.0. One stray environment variable — copied from another project, or misread from a document — publishes the whole API on the LAN, and with an IPv6 pinhole open, potentially further.

Fix: refuse non-loopback, non-private addresses unless an explicit override variable is set, and log a warning on every non-loopback bind. This is a fail-safe defaults problem: the system relies on the operator not making a mistake instead of refusing the dangerous configuration.

References: CWE-1188 · CIS Controls v8.1 Control 4 · CISA Secure by Design.

Cleartext permission is app-wide Low

Plain HTTP inside the tunnel is fine and defensible: WireGuard already provides confidentiality and authenticity, and TLS on top would be redundant encryption over an already authenticated channel. The problem is that usesCleartextTraffic="true" applies to the entire app, so a Bridge URL pointing outside the tunnel would also travel in the clear, silently.

Fix: replace the blanket flag with a network security configuration that permits cleartext only for the tunnel subnet.

References: OWASP MASVS MASVS-NETWORK-1 · Android Network Security Configuration.

No rate limiting, no audit trail Low

Once a token exists, nothing throttles attempts against it. And there is no record of who called what, so "what ran, from which peer, when" is currently unanswerable.

Fix: progressive backoff on authentication failures; structured audit logging with timestamp, source, route and result — and no prompt content in the logs.

References: CWE-307, CWE-778 · CIS Controls v8.1 Control 8 · NIST CSF 2.0, Detect function.

Debug keystore signing Low internally

The release APK is signed with the repository's debug certificate, which is public and reproducible — anyone can build an APK Android will accept as a legitimate update of the same package. For one phone installed over USB this is theoretical. The moment the APK is distributed by any other means, it is not.

Fix: a private release keystore before any distribution, stored outside the repository, with a backup.

Leftovers from the SSH design Medium

If you followed an earlier version of this guide: sshd is probably still installed, running and listening on all interfaces, and APKs built before the migration still contain the embedded key — they keep working until it is revoked.

Fix, in order: remove the app's key from authorized_keys (this alone invalidates every old APK); then, if nothing else on the machine needs it, stop and disable sshd and close its router rule.

The repository side is already done: the SSH transport, its native module and every SSH build variable have been removed, so current builds contain no credential to revoke. What remains is host state you have to clean up yourself.

References: MITRE ATT&CK T1133 External Remote Services, T1078 Valid Accounts.

Hardening plan

Ordered by impact-to-effort, not by preference.

  1. Close the authorization gap. Token on the bridge and in the app, wildcard CORS removed, Host validated, bind guard added, filesystem browsing scoped.
  2. Shrink the blast radius and gain visibility. Cleartext limited to the tunnel subnet, rate limiting, audit log, private release keystore, bridge running as a persistent service.
  3. Structural hardening. Retire sshd, per-peer preshared keys, QR-code pairing instead of a typed token, scheduled key rotation, periodic peer inventory review.
Why QR pairing instead of a typed token

Saltzer & Schroeder called it psychological acceptability: a control with too much friction gets switched off by the very person it protects. A token you must retype on a phone keyboard is exactly that kind of control.

Rules that do not change

  • One key pair per device, one /32 per peer. Never share a key between devices.
  • Private keys never leave their machine. Not into a terminal, a document, a chat, or an issue. Generate them by redirecting into a file and restrict the ACL.
  • Split tunnel. AllowedIPs on the device carries the host address only — never 0.0.0.0/0.
  • One entry port. UDP for WireGuard, and nothing else. Never forward the bridge port.
  • The bridge never binds to a public address. Verify it on every start, not from memory.
  • Nothing secret in the repository. No .env, keystores, keys or tokens. Treat logs as sensitive.
  • Public keys are not secrets, but they are identifiers. Neither they, your public IPv6 address, your dynamic DNS name nor your external port belong in a public repository — that is target information, not design.

That last rule is Kerckhoffs's principle applied honestly: a system must remain secure with its design public — which is why this guide exists — while the keys stay secret. Identifiers sit in between: publishing them buys nothing and costs exposure.

If you only follow two

Track CISA's KEV catalog and the SANS Internet Storm Center. Both answer "does this affect me today?", which is a different and more useful question than "is this theoretically insecure?".

Worth reading

  • Saltzer & Schroeder, The Protection of Information in Computer Systems (1975). Fifty years old and still the best checklist there is. Three of their eight principles name the gaps on this page exactly: complete mediation (check every request, not just the ones from outside), fail-safe defaults (deny by default), and least privilege.
  • Ross Anderson, Security Engineering, 3rd edition — freely available from the author. The chapters on access control and the economics of security explain why gaps like these are so common: it is rarely ignorance, it is sequencing.
  • Adam Shostack, Threat Modeling: Designing for Security. The STRIDE method is the cheapest way to produce the asset table at the top of this page without relying on intuition.
  • Gilman & Barth, Zero Trust Networks (O'Reilly). The implementable version of SP 800-207, and it addresses this exact trap: "I have a VPN, therefore I am secure."
  • Jason A. Donenfeld, WireGuard: Next Generation Kernel Network Tunnel (NDSS 2017). The protocol whitepaper — why there is no cipher negotiation, and why invalid packets get no reply. wireguard.com/papers
  • Bruce Schneier, on attack trees and the observation that security is a process, not a product. The practical consequence: a security page that is never revisited stops being true.
